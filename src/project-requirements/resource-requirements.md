### Resource Requirements

The primary resource constraint for this system is model memory allocation. When a model's parameter count exceeds the available VRAM capacity of the host GPU, Ollama resorts to partial GPU offloading, retaining the remaining layers in system RAM. This split-memory configuration represents the most common performance bottleneck in consumer-grade deployments and imposes a substantial demand on host memory that scales with the proportion of the model that cannot be accommodated at home.

The consequence is measurable degradation in inference performance: per-token latency increases and overall token throughput falls, as each forward pass incurs the cost of data transfers between host and device memory that would be absent in a fully VRAM-resident configuration. Token throughput - the number of output tokens generated per second - is therefore the primary practical metric for assessing the assistant's usability, since generation rates below an interactive threshold disrupt the feedback loop that developer tooling demands.

Context window size is an additional parameter that simultaneously governs several interdependent capabilities of the deployed model. A larger context window allows the model to retain a longer multi-turn conversation history without truncation, preserving coherence across extended interactions. However, this budget is shared: when tool definitions are injected into the prompt at inference time, they consume a portion of the available context tokens, directly reducing the capacity remaining for conversation history and for document chunks retrieved via RAG.

Retrieved knowledge-graph nodes and tool schemas compete for the same fixed allocation: increasing the volume of retrieved knowledge necessarily compresses the conversational context, and vice versa. A model selected with an insufficient context length therefore constrains not only conversational continuity but also the system's capacity to perform tool use and incorporate retrieved knowledge concurrently.

Beyond memory constraints, the system carries a hard runtime dependency on an externally managed Ollama server being accessible over the network at both development and presentation stages. Unlike an embedded inference library, Ollama operates as a standalone service whose availability cannot be assumed and must be explicitly provisioned as part of the deployment environment.
